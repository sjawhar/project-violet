# Engine & Agent-Tooling Assessment: Can Agents Build Direction D (2.5D) for Violet?

## 1. Verdict

**For Direction D (3D-rendered world, 2D side-scrolling gameplay), Godot 4.7.2 is the engine agents can operate better on this devbox today — moderate-high confidence.** Unity 6.3 LTS has the stronger *built-in* 2.5D feature set (native 3D-objects-under-2D-lights blending, shipped Oct 2025) and the richer official MCP tooling, but on this specific machine it carries real operational drag: a COSMIC-specific Editor bug that was open for eight months (Oct 2025–Jun 2026), a paid/account-gated path to the best-supported AI tooling, and a June 2026 Terms-of-Service change whose scope for local MCP use only got informally clarified, not fixed in writing. Godot's 3D feature set is thinner (no native LOD streaming, no terrain/chunking system, real-time shadows visibly weaker than baked), but it is MIT-licensed with no account gate, its shader-stutter problem (the one 3D-relevant Godot pain point) was fixed engine-wide in 4.4 (2025), and its community MCP ecosystem, while smaller, already includes runtime bridges that drive the *running game* (input injection + screenshot + record/replay) rather than editor-only automation — which is what an agent-driven playtest loop actually needs.

**Confidence caveat:** no shipped commercial game currently combines "fully 3D-lit, non-pixel-art, side-scrolling gameplay" in Godot — the best shipped precedent (*Until Then*, Godot 4.1, 2024) is pixel art rendered in 3D space, not GRIS/Planet-of-Lana-style lit 3D. This is a gap for both engines relative to Direction D's visual bar, not just Godot's; Unity has no better shipped precedent either. The bake-off in §4 is designed to close this evidence gap directly rather than rely on inference.

## 3. Failure Modes / Gaps

1. **Aesthetic-layout blindness (both engines, worse for Unity today):** the single most consistent 2026 report across both communities is that agents are good at *wiring* (references, layers, physics, animators, tests) and bad at *composition* (object placement that reads well, material counts, "does this look like a game"). This directly threatens Violet's core visual promise — a GRIS/Ori-tier world — because the agent will nail the mechanic and miss the mood without a tight screenshot-review loop.
2. **Unity's account/subscription dependency for the *good* path.** The free community MCPs work, but the officially-supported, best-integrated path (screenshots, checkpoints, console access, profiler) sits behind a $10/mo Unity Cloud subscription per seat — a recurring cost and a third-party account Sami didn't ask for, layered on top of whatever coding-agent subscription is already paying for the work.
3. **Unity ToS ambiguity is unresolved in writing.** Even with the favorable forum clarification, a solo indie project that leans entirely on CoplayDev/unity-mcp for local automation is building on a policy Unity could tighten unilaterally; there is no contractual carve-out, only a discussion-thread reassurance (Sept 26 2026 status).
4. **Godot's missing native 3D infrastructure means the agent must write more from scratch:** no LOD streaming, no terrain/chunking system, weaker baked shadows than Unity — for a level-sized game (5–8h) this is probably fine, but it shifts risk onto the agent's ability to write correct custom systems (asset streaming, world partitioning) rather than configure a built-in one, and that is exactly the kind of infrastructure code where a bug is silent until it isn't.
5. **Editor-only vs. runtime-bridge MCP split in Godot.** The most-starred, most-mature Godot MCP (Coding-Solo, 5.8k★) cannot drive the *running* game — it only edits the project. The servers that can (godot-mcp-toolkit, IvanMurzak/Godot-MCP) are newer and thinner in adoption evidence. A commercial-quality agent playtest loop needs the second category to mature, or Sami's team needs to stitch two servers together.
6. **Neither engine has a first-party, agent-legible visual-regression story for a from-scratch 2.5D project.** Unity's Graphics Test Framework is mature but built for engine/render-pipeline regression testing, not "does this hand-authored level look right"; Godot's community pixel-diff runner is only two months old (July 2026) as of this writing.
7. **Shipped-precedent gap.** No engine has a shipped, commercial, *lit* 3D side-scroller (not pixel art) built primarily by AI agents — the entire premise of Direction D at commercial-indie quality is currently untested at scale on either engine. The bake-off below exists specifically because this can't be answered by more searching.

## 4. Proposed Bake-Off (both engines, same text-layout input, ≤1 hour of Sami's judging time)

**Shared setup:** one YAML/LDtk text layout describing an 8–15 "room" greybox level on the X/Y gameplay plane with per-room color tags (red/green/blue), a start and an exit, one dash-gap, one stomp-breakable floor. Same brief handed to an agent working in each engine, cold (no engine-specific hints beyond "use the MCP/tooling available").

| # | Task | Pass (2) | Partial (1) | Fail (0) |
|---|---|---|---|---|
| 1 | **Greybox from text.** Agent parses the layout and instantiates modular 3D blockout pieces along the plane, tagging each room's platforms to the matching color layer/group. | Level topology matches the layout 1:1 in a top-down screenshot; every tagged object verifiable by log dump or Inspector spot-check (5 samples); zero console errors. | Topology mostly right, 1–2 tag mismatches, or console warnings. | Level doesn't load, topology diverges, or tags absent. |
| 2 | **Resonance toggle.** Agent wires a runtime toggle: pressing a key (a) flips collision for one color layer and (b) drives a grayscale→color reveal (Unity Volume/renderer-feature or Godot shader uniform) for the same tagged geometry only. | Two screenshots (off/on) show geometry-matched desaturation and collision toggling confirmed via an automated test (Play Mode / gdUnit4) asserting the boolean state before and after. | Visual or collision half-works (e.g., color reveals but collision doesn't, or vice versa). | Neither behavior is correct or it crashes. |
| 3 | **Character run/jump/dash.** Agent wires or generates a rigged character with the three movement states confined to the plane. | Automated test asserts state transitions (idle→run→jump→dash) and a screenshot sequence shows a physically plausible jump arc and a successful dash across the level's dash-gap. | States exist but one transition is wrong/missing, or the arc looks physically broken. | Character doesn't move or crashes on input. |
| 4 | **Headless screenshot playtest.** Agent scripts an input path from start to exit and runs it headless (Unity: keep graphics device, batchmode; Godot: `--headless` + `xvfb`), capturing 5 screenshots at fixed waypoints and reporting pass/fail against "reached exit, no fallthrough, dash-gap cleared, stomp-floor broke on cue." | Runs unattended in under 10 minutes, produces a written pass/fail plus 5 screenshots Sami can eyeball in under 5 minutes and confirm they match the checklist. | Runs but needs manual intervention, or screenshots are ambiguous/missing a waypoint. | Doesn't run headless at all, or requires the Editor GUI open. |

**Scoring:** 8 points max per engine. **≥6 = commercially-viable agent workflow for D** (proceed with agent-built content, human passes for polish only). **3–5 = usable with heavy correction** (agent drafts, human rebuilds art/composition every iteration — probably not worth D's premium over A/C). **<3 = not viable** for D on this timeline; fall back to Sami's own ruling ("otherwise A. C is also reasonable").

## 5. Costs

- **Godot:** $0 engine/tooling cost. All MCP servers found (Coding-Solo, godot-mcp-toolkit, IvanMurzak/Godot-MCP) are free/open-source. Only cost is whatever AI coding-agent subscription is already in use (Claude/GPT), unaffected by engine choice.
- **Unity:** $0 if relying solely on community MCP (CoplayDev/unity-mcp, free/MIT) driven by an existing Claude/Codex subscription — no Unity Cloud credits consumed via the AI Gateway path. If using Unity's own AI Assistant/official MCP: 14-day/1,000-credit free trial (credit card required, auto-converts), then **$10/mo minimum** for Personal tier, or bundled into Pro/Enterprise (no incremental cost if already paying for Pro). Extra credits ~$20/2,000.
- **Compute:** $0 incremental — both run on the existing iGPU/CPU locally; no cloud GPU rental needed for either engine's headless/CI story at this project's scale.
- **Hidden cost:** Unity's ToS ambiguity (§3.3) is a *risk* cost, not a dollar cost — potential future need to migrate off community MCP if Unity tightens enforcement.
